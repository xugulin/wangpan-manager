# 第二步实验：纯 HTTP 登录能否拿到 pan 域 STOKEN

**目的**：决定"不跑 JS 的自研登录器"这条路成不成立 ——
成立就能省掉 209 MB 的浏览器引擎，不成立就立刻止损（别再往这个方向投时间）。

## 背景（为什么必须做这个实验）

我们已经用真机证据钉死：

* 百度**扫码登录**得到的 BDUSS 进不了网页版 pan 域（`/disk/main` 被重定向到
  `errmsg=Auth Login Params Not Corret`），服务端**不下发 pan 域 STOKEN**；
* 写操作（上传/改名/删除）恒 `errno:-6` —— 因为 pan 域 STOKEN 只在
  **真正的网页版登录**时才下发；
* 所以「内置浏览器登录」的唯一价值就是"它跑的是真网页版登录"。

那么问题变成：**不渲染页面、直接打百度的登录接口（纯 httpx），能不能拿到
pan 域 STOKEN？**

## 怎么跑

```bash
cd ~/python/网盘管理
运行环境/venv/bin/python ~/v8_3_工作区/逆向/实验_纯HTTP能否拿STOKEN.py \
    --账号 你的账号 --报告 ~/v8_3_工作区/日志/实验报告.txt
```

* 密码用 `getpass` **交互输入**（不回显、不进 shell 历史、不落盘）；
* 也可以用 `--账号` 先把账号填好，密码仍然交互输入；
* 报告里所有 cookie 值都**只留长度与前 4 字符**，可以放心贴出来。

## 脚本会做什么（每一步都有输出）

| 步骤 | 动作 | 想看到什么 |
|---|---|---|
| ① | 打开 `pan.baidu.com` 拿基础 cookie | HTTP 200 |
| ② | 打开登录页、尝试取 `token` | 取到或"接口不强制" |

| ③b | **带 BDUSS 再进一次 `pan.baidu.com/disk/main`** | 这一步很关键：网页版就是靠访问 pan 域才换到 STOKEN 的，少了它会误判 |
| ④ | 摊开所有 cookie（按名字 + 域名） | **有没有 `.pan.baidu.com` 域的 `STOKEN`** |
| ⑤ | 若拿到凭证：用项目适配器打一次 `/api/list`（读）+ `/api/create`（建一个随机名目录，**成功立刻删除**） | `errno:0` = 可写 |

## 安全承诺

* 不落盘任何凭证（密码只在内存；会话文件用**临时覆盖 + 结束时还原**，会打印"已还原"）；
* 写探针只建一个随机名目录并立刻删除，不碰你的任何文件；
* 报告脱敏，可安全分享。

## 结论怎么读

| 现象 | 含义 | 下一步 |
|---|---|---|

### 终端放不下怎么办（用户反馈"二维码太大扫不了"）

实测结论：**百度登录二维码本来就装不进普通终端。**

| 编码 | 模块数 | 终端占用 |
|---|---|---|
| 百度原始图片 | 53×53 | **110 列** |
| 解出内容后用纠错级别 L 重编 | 53×53（URL 136 字符） | 约 112 列 |
| 早期测试用的短 URL（120 字符） | 43×43 | 90 列 |
| 再短的变体（75 字符） | 35×35 | 74 列 ✅ 能放下 |

也就是说：**只有把 URL 砍到 80 字符左右才可能塞进 80 列终端** —— 但那些参数
（`sign`/`t`/`qrloginfrom`…）是服务端用来校验扫码的，**不能乱删**，删了极可能
扫了也登录不上。所以不做这种"为了好看而破坏功能"的优化。

现在的行为（`终端扫码登录百度.py`）：

1. 先解出二维码内容 → 用**纠错级别 L + 静默区 1** 重编（比原始小一截）；
2. 按**终端实际列数**自动挑放大倍数（1 模块 = 2/4/6 个字符），能放下就直接画；
3. 放不下时打印三条**真的能用**的路：
   * ① 二维码已存成图片：`数据/终端二维码.png`（实测 zbar 能解出来），
     用看图工具打开即可扫：`xdg-open 数据/终端二维码.png`；
   * ② 把终端拉到需要的列数以上再跑；
   * ③ **二维码内容就是那个链接**：用手机浏览器打开它也能完成登录
     （最省事，不用扫码）；
4. 另外一直可以用图形界面：「网盘页 → 登录/管理 → 🌐 用内置浏览器登录」。

### 二维码怎么画得更小（参考 QuarkPan）

用户提到 [lich0821/QuarkPan](https://github.com/lich0821/QuarkPan) 的二维码画得更小。
查了它的实现（`quark_client/utils/qr_code.py`，1465 字节，很短）：

```python
def print_ascii_qr(text: str):
    import qrcode
    qr = qrcode.QRCode(border=1)   # 边框小一些，方便在终端放大显示
    qr.add_data(text); qr.make(fit=True)
    qr.print_ascii(invert=True)    # 反相打印（部分终端/主题需要关闭 invert）
```

**关键就在 `qrcode` 自带的 `print_ascii`**（读它的源码）：

```python
codes = [bytes((code,)).decode("cp437") for code in (255, 223, 220, 219)]
#        = [' ', '▄', '▀', '█']
for r in range(-border, modcount + border, 2):        # ← 每次跨 2 行
    for c in range(...):                              # ← 每列只输出 1 个字符
        pos = get_module(r, c) + (get_module(r + 1, c) << 1)
        out.write(codes[pos])
```

也就是说：**一个字符表示上下两个模块**（空格=白白、▄=白黑、▀=黑白、█=黑黑），
于是

| 画法 | 宽度 | 高度 |
|---|---|---|
| 我原来用的 `■■`（一个模块两个字符） | `2 × 模块数` | `模块数` 行 |
| **QuarkPan / qrcode 自带**（半块字符） | **`模块数`** | `模块数 ÷ 2` 行 |

宽度**直接减半**，高度也减半 —— 47 模块的二维码只占 **47 列 × 24 行**，
普通 80 列终端当然放得下。再加上 `border=1`（标准静默区是 4）又省 6 列。

### 本项目已改成同样的画法

* 默认：**1 模块 = 1 字符**，用 `▄/▀/█/空格` 画上下两行模块；
* `--纯文本`：保留原来的 `■■` 画法（兼容不支持块字符的终端，宽度翻倍）；
* 仍然保留"解出内容 → 纠错级别 L 重编 → 按终端列数自动缩放"这套适配
  （窄终端优先保证能放下）。

实测（真实百度登录二维码，URL 223 字符）：

```
L 级重编：55×55 模块
终端 80 列  → 放大 1 → 30 行 × 55 列   ✅ 放得下
终端 100 列 → 放大 1 → 30 行 × 55 列
zbar 扫"字符画还原图"：✅ 内容一致（可扫）
```

**结论**：之前"装不下"的根因是我的画法宽度翻倍（一个模块两个字符），
不是二维码本身太大。改成半块字符后，80 列终端也能直接扫。

### 踩坑：扫码确认后终端被"没有正在等待的扫码会话"刷屏

**现象**（用户实测）：手机扫码 + 点确认后，终端里瞬间刷满
`× 失败：没有正在等待的扫码会话`，看起来像登录失败。

**根因**：是**脚本的锅**，不是登录失败。`v8_3/桥/后端_百度.py::login_qr_wait`
在返回前会 `finally` 里把这条扫码会话**关掉并删除**（一次等待 = 一条会话的
生命周期）。而脚本原来写成"每次只等 8 秒，超时就拿同一个会话再等一次"的循环 ——
第一次调用返回后会话已经没了，后面每一次重试都立刻失败，于是把屏幕刷满。

**修法**：把整个等待预算**一次交给桥**（桥内部本来就每 20 秒切片 + 打进度），
只调一次 `扫码等待`；返回后按状态一次性给结论，不再重试。

教训：桥侧"一次调用即消费掉会话"的接口，调用方不能自己写重试循环。

# 🔬 判决性实验（2026-09-20）：pan 域 STOKEN 到底靠什么拿到

## 实验设计

用户指出"用手机短信登录"更现实（账号密码之后还有短信验证）。为了不再猜接口，
先做了一个**不需要复刻任何登录接口**的判决性实验：

> **一个"真网页版登录"（用户刚在浏览器里短信登录成功）拿到的 BDUSS，
> 用纯 httpx 访问 pan 域，能不能换到 pan 域 STOKEN？**

如果**能** → 任何能拿到 BDUSS 的登录方式（扫码/短信/纯 HTTP 复刻）都能自己换成
可写会话 → **浏览器引擎不必内置**（省 209 MB）。
如果**不能** → 服务端还要看浏览器指纹/JS 执行 → 真浏览器渲染是硬要求。

## 结果（脚本：`~/v8_3_工作区/逆向/实验_BDUSS换panSTOKEN.py`）

浏览器（CDP 取 cookie，确认已登录）侧：

```
cookie 名：BAIDUID、BDUSS、BDUSS_BFESS、STOKEN、STOKEN_BFESS、PTOKEN、
          PANPSC、csrfToken、HISTORY、UBI、XFI、XFT …
BDUSS：取到（tLSUNvRn…）        ← 网页版登录换来的
pan 域 STOKEN 在浏览器里： True   ← 浏览器里有
```

纯 httpx（**只带这个 BDUSS**，带正常 UA/Referer，跟随重定向）侧：

```
GET https://pan.baidu.com/disk/main          → HTTP 200，最终地址没被踢
   ↓ Set-Cookie PANPSC（域 pan.baidu.com）    ← 只有"清空"用的 PANPSC
GET https://pan.baidu.com/api/list?dir=/     → {"errno":-6,...}
结论：纯 httpx 访问 pan 域后，pan 域 STOKEN ❌ 没拿到
      （cookie jar 里只有 BAIDUID / BAIDUID_BFESS / PANPSC / csrfToken / newlogin）
```

补充：`passport.baidu.com/v2/api/` 上那些"不带正确查询串就 404"的接口一律
回 404（nginx），我未能用纯 HTTP 复现出"有效会话"的判据 —— 这条也说明
**纯 HTTP 侧连"证明自己已登录"都做不到**。

## 三条实测结论（决定路线）

| # | 结论 | 证据 |
|---|---|---|
| 1 | **扫码登录的 BDUSS 拿不到 pan STOKEN** | 前一轮实测：`/disk/main` 被重定向到 `errmsg=Auth Login Params Not Corret`；`补齐 bdstoken 失败 errno:-6` |
| 2 | **网页版（短信）登录的 BDUSS，用纯 HTTP 复用也拿不到 pan STOKEN** | 本次实验：只带 BDUSS 请求 pan 域 → 没有 STOKEN、`errno:-6` |
| 3 | **浏览器里有 pan STOKEN** | CDP 取到的 cookie 里 `STOKEN`（域 `.pan.baidu.com`）存在，且写操作实测可用 |

**因此**：pan 域 STOKEN 的发放**不是"拿到某个 cookie 就能换"**，而是与
"浏览器里真实执行了网页版登录流程"绑定（登录页要跑设备指纹
`mkd.js`/`fingerprint.js`、风控 `loginv5`/`hercules bundle`，pan 域的换发
也在浏览器上下文里完成）。

## 对"省掉浏览器引擎"的影响

* **纯 HTTP 复刻登录（无论扫码/密码/短信）→ 最多只能拿到"只读会话"**，
  写权限拿不到；
* 唯一稳的写权限来源是**真浏览器渲染的网页版登录**（内置浏览器 / 用户自己的
  浏览器导入）；
* 所以"自研登录器替代 QtWebEngine"这条路**在写权限上不成立**；
  能省的只有"Windows 用系统 WebView2"（0 体积、仍是真浏览器）或
  "出无内置浏览器的精简包，让用户用自己的浏览器"。

## 顺带记录：HAR / 抓包工具的现状

* 为了抓短信接口，写了两个工具（都在工作区，不进仓库）：
  * `抓短信接口.py`：CDP 连浏览器面板 → **在页面里挂钩 XHR/fetch** →
    轮询读回请求（URL/方法/POST 体，自动脱敏）。比 CDP 的 Network 事件可靠
    （本机实测 Network 事件一条都收不到）；
  * `工具/洗HAR.py`（**进仓库**）：把浏览器导出的 HAR 洗成可安全分享的样子
    （Cookie/凭证/手机号/验证码全部脱敏，POST 体保留结构）。
* 但**这次结论已经不需要短信接口了** —— 因为结论 2 已经证明：
  即使把短信登录复刻成纯 HTTP，拿到的还是会话仍然换不到 pan STOKEN。

# 百度短信登录的实现方式（2026-09-20，最终结论）

## 为什么不做"纯 HTTP 短信登录"

把百度登录页的 JS 扒下来看过（`loginv4_tangram_4e0e15d.js`，593 KB），实测结论：

| 线索 | 结果 |
|---|---|
| `POST passport.baidu.com/v2/?getphonestatus`（`phone` + `loginVersion=v4`） | **活着**：返回 `{"errInfo":{"no":"0","msg":"已存在","isPwd":"1"}}`（能判断账号是否存在/有无密码） |
| `?getsmscode`、`?getpasscode`、`?getphonelogininfo`、`?checkphone` | **全部 404**（nginx 直接拒） |
| `?loginspmbindmobilesend`、`?bindmobilesend`、`?sendmobilesms`、`sapi/authwidgetverify` | **全部 404** |
| `POST ?regphonesend` | 回 200 但**响应为空、手机收不到短信**（实测两次都没收到） |
| JS 里的真实路径 | 短信登录走 `passport.pop.ArmorWidget("bindmobile", {token: bindMobileToken, authsid, …})` —— **ARMOR 风控组件**，接口在它自己的 JS 里 |

所以：**百度的短信登录是登录框里的 ARMOR 组件（跨域 iframe + 设备指纹 + 风控），
纯 HTTP 复刻不出来**；而且即使复刻出来，按上一节的判决性实验，拿到的 BDUSS
也换不到 pan 域 STOKEN（写权限还是要真浏览器）。

## 于是实现方式：「内置浏览器 + 自动切到短信登录」

用户在程序里点一下，程序打开**内置浏览器**（真 Chromium），自动：

1. 加载 `pan.baidu.com`；
2. 用 JS 按**文字**找「短信登录」tab 并点它（重试 12 次 × 0.5 秒，因为登录框是异步渲染的）；
3. 把用户在短信面板里填过的**手机号自动填进登录框**（连 `encryptMobile`
   隐藏域一起设 —— 百度会把手机号 base64 塞进这个域）；
4. 用户只需点「发送验证码」→ 填验证码 → 登录；
5. **登录成功后程序照旧自动取走完整会话**（含 pan 域 STOKEN），并当场验写权限。

对应改动：

| 文件 | 改动 |
|---|---|
| `v8_3/界面/浏览器引擎.py` | 接口新增 `执行JS(脚本)`（页面内小动作用；按文字找元素比记 class 稳） |
| `v8_3/界面/引擎_QtWebEngine.py` | `执行JS` 实现：`runJavaScript` 异步 → `QEventLoop` + 2.5 秒超时转同步 |
| `v8_3/界面/内置浏览器登录.py` | 构造支持 `登录方式="sms"` 与 `手机号=`；新增 `_切到短信登录()`、`_填手机号()`（带重试上限） |
| `v8_3/界面/登录对话框.py` | 短信面板新增「📱 用内置浏览器短信登录（推荐）」，并把手机号带进窗口 |
| `v8_3/桥/后端_百度.py` | `auth_caps.sms` 从"不支持"改成"支持"，说明写清为什么走内置浏览器 |
| `工具/界面自检.py` | 新增：短信方式会执行切页 JS、会自动填手机号（假引擎离线验证） |

# ⚡ 内置浏览器登录提速（2026-09-20）

用户反馈"内置浏览器登录流程耗时太长"，先量了一遍到底慢在哪
（脚本：`~/v8_3_工作区/逆向/测内置浏览器耗时2.py`）：

| 环节 | 耗时 | 结论 |
|---|---|---|
| 建引擎（profile + 视图） | **0.0 秒** | 不是瓶颈 |
| 单次取 cookie（直读 sqlite） | **~0 毫秒** | 不是瓶颈 |
| 执行 JS 往返 | **1~2 毫秒** | 不是瓶颈 |
| 打开 pan.baidu.com → loadFinished（**冷启动**） | **4.2 秒** | ← 就是它 |
| 打开 pan.baidu.com → loadFinished（**热启动**） | **2.6 秒** | ← 就是它 |

**结论：慢的只有"打开百度首页"那 2.6~4.2 秒**，其余环节都是毫秒级；
而这几秒完全可以提前做掉。

## 做了什么：预热登录页（`v8_3/界面/预热登录页.py`）

1. **程序启动 2 秒后**：对"本地没有会话文件"的网盘，在**隐藏宿主控件**里起一个
   登录引擎并开始加载登录页（有会话的网盘跳过 —— 不需要登录页，别白占内存）；
2. **打开登录对话框、切到扫码/短信方式**时：再确认预热一次；
3. 点「用内置浏览器登录」时，窗口**接管这个已经加载好的引擎**
   —— 视图加进布局时 Qt 自动换父，**不会重新加载页面**；
4. 登录完成/关窗后把预热引擎从池子里摘掉（`关掉全部预热()`），不留后台渲染进程。

**实测效果**：

```
预热发起耗时            0.10 秒（只是起引擎 + 发导航，页面在后台加载）
接管后打开登录窗口耗时  0.51 秒   ← 以前要先等 2.6~4.2 秒
状态栏                  🔥 已接管预热好的登录页（省下一次加载）
```

## 踩到的两个坑

1. `QWebEngineView` 的父对象**必须是 QWidget** —— 传 `QApplication` 直接
   `TypeError`，所以预热引擎挂在一个隐藏宿主控件上；
2. 宿主控件的销毁**不能交给 QApplication 一起析构**：QtWebEngine 的析构顺序很难伺候，
   实测会让自检进程在退出时**段错误**（检查项全绿、退出码 139）。
   现在宿主注册到 `aboutToQuit` 上销毁，另外自检脚本用 `V8_3_不预热=1` 跑
   （预热只是提速，不是功能）。

## 还没解决 / 需要留意的

* 自检在"整份脚本 + 真实预热引擎"同时存在时，退出仍会偶发段错误；
  单独跑（预热 / 登录窗口 / 两者都做）都正常 —— 定位为 **QtWebEngine 在脚本化
  反复建销 profile 时的析构问题**，真程序（只建一个 profile、正常退出）没有这个现象；
* 如果你在真程序里遇到"退出时报错"，告诉作者，我们再顺着 `aboutToQuit` 的时序查。

### 用户实测反馈：接管预热后"窗口一片空白"

现象：点「📱 短信登录（内置浏览器跳转，推荐）」→ 窗口出来了、地址栏也对
（`https://pan.baidu.com/disk/main`），但页面**一片空白**，状态栏停在
"正在加载登录页…"。

原因：预热是在**隐藏控件**里导航的，实测存在"那次导航早就停了、页面从没渲染出来"
的情况 —— 接管过来就是一个白板。

修法（两层）：

1. **接管时先判断要不要重来**（`_像是白板()`）：
   * `引擎.加载中()`（`QWebEnginePage.isLoading()`）为真 → 判定"还没画出来"；
   * 用 `执行JS("document.body.innerHTML.length")` 看文档是不是几乎空的（< 200）；
   * 判定为白板就**在窗口已经可见的情况下重新加载一次**（这时候渲染没问题）；
   * 判定正常就照旧"接管、不重新加载"（保住提速）。
2. **加载完之后再兜一次**：`_加载完` 里如果发现文档还是空的，
   自动重载一次（`_救过一次` 标记，最多救一次，避免死循环）。

引擎侧新增 `加载中()` / `重新加载()`（接口 + QtWebEngine + 假引擎三处都实现）。

自检新增：`预热页面还在加载时，接管会强制重开一次（打开次数 2）` —— 498 项全绿；
真显示（Xvfb）下复测接管截图：**非白像素 9304**（正常渲染，不是白板）。

# ❌ 预热为什么被删掉（2026-09-20 的结论）

先做了"预热登录页"（启动时用隐藏控件先加载登录页，点登录时接管那个视图），
当时量到"打开窗口 0.5 秒"，看起来很美。**但用户实测两次都是窗口一片空白**，
于是回头把账算清楚：

## 三次踩坑

| # | 现象 | 原因 |
|---|---|---|
| 1 | 点登录 → 窗口一片空白 | 预热是在**隐藏控件**里导航的：QtWebEngine 在隐藏视图里加载/渲染不可靠，接管过来就是白板 |
| 2 | 修了白板检测后仍然白 | 把 `QWebEngineView` 从一个父控件换到另一个父控件，QtWebEngine **不保证重绘** |
| 3 | 量出来的"提速"是假的 | 我用 `loadFinished` 当计时终点 —— 但**百度首页是 SPA，`loadFinished` 经常压根不触发**，于是"2 秒/17 秒/27 秒"这些数字毫无意义 |

## 真正可靠的结论（真显示 Xvfb 下实测）

| 场景 | 第一个"有内容的画面"出现耗时 |
|---|---|
| 窗口自己加载（profile 全新） | **2.96 秒** |
| 窗口自己加载（缓存已有） | **0.16 秒** |

**也就是说：HTTP 缓存自己就热了** —— 第一次 3 秒，之后 0.2 秒以内。
预热那套（隐藏控件 + 视图换父）**没有可量化的收益，却带来了白板风险**。

## 现在的做法

* **删掉整个预热模块**（`v8_3/界面/预热登录页.py`），窗口永远用自己的视图 —— 可靠优先；
* 保留两条**防白板兜底**（这次是真需求）：
  * `_像是白板()`：还在加载、或 `document.body.innerHTML.length < 200`；
  * 打开页面后 **4 秒**自己查一次（SPA 的 `loadFinished` 不一定来），是白板就重载一次并提示；
  * `loadFinished` 来了也会查一次（同样只救一次，避免死循环）。
* 自检里加环境变量 `V8_3_只用注入引擎=1`：**自检一律用假引擎**，
  不再建真 QtWebEngine（顺带解决"自检退出时段错误"那个 Qt 析构问题）。

## 教训（写给未来的自己）

1. **别用 `loadFinished` 给 SPA 计时** —— 它可能永远不来；要看"页面里出现目标元素"这种
   内容级判据；
2. **隐藏控件里加载页面 + 视图换父** 这两件事在 QtWebEngine 上都不可靠，
   别拿它们当提速手段；
3. 提速方案必须**先证明可靠**（真显示下截图对比），再谈秒数。

# 🎬 修「多出来一个超出屏幕的 VLC 窗口」（2026-09-20）

**现象（用户实测）**：播放时 GUI 里在放视频，同时**多出一个很大的、超出屏幕的窗口**
也在放同一个视频（标题栏写着 `VLC media player`）。

## 定位

这个项目本来就有「游离窗口」机制（`v8_3/播放/游离窗口.py` + `v8_3/界面/游离窗口守护.py`）：
libvlc 在 `set_xwindow` 那一刻如果拿到的是"还没映射到屏幕"的窗口号，就会**自己开一个顶层
窗口**放画面。守卫每 2~3 秒扫一次 X 的顶层窗口（认 `WM_CLASS=vlc` / 标题
`… - VLC media player`），发现就"自愈"（把画面收回来），收不回就关掉它。

实测确认这套**能收**（真起一个 `vlc` 窗口验证：守卫找到 2 个、关闭成功、最后 0 个）。

那用户看到的"两个窗口都在放"是怎么来的？看自愈路径：

```
_自愈画面() → 会话.起播(新句柄) → VLC.绑定窗口(新句柄) → VLC.播放(地址)   ← 重播
```

而 `绑定窗口()` 只调 `libvlc_media_player_set_xwindow` —— **播放中改它不会搬走已有的
视频输出**；紧接着的 `播放()` 又从头放一次，libvlc 于是在**新句柄上再开一个 vout**，
老窗口还活着 → "两个窗口都在放同一个视频"，而 VLC 自己开的那个往往很大、还超出屏幕。
**换句话说：自愈本身把窗口从 1 个变成了 2 个，而且没有上限地重复自愈。**

## 修法（三层）

1. **停止并等待**（`vlc绑定.VLC.停止并等待(超时秒)`）：`stop` 之后轮询状态直到真的
   `已停止/已结束/出错`（vout 释放是异步的，不等到位就换绑 = 还是两个窗口）；
2. **换绑前先停住**（`播放核心.起播`）：只有句柄真的变了才停；自愈回调也改成
   "先停 → 再绑 → 再播"；
3. **自愈有上限**（`游离窗口守护`）：最多自愈 2 次，之后**只关窗口不再自愈**，
   并在日志里告诉用户怎么手动恢复（点「独立窗口」按钮或重新点 ▶）。
   另外日志里会报游离窗口的**尺寸**（诊断"超出屏幕"）。

## 验证

* 真起一个独立 `vlc` 窗口 → 守卫找到并关闭成功（`测守卫收窗口.py`）；
* 单测新增 3 项：自愈到上限后不再自愈、日志带尺寸、到上限仍会去关窗口；
* 播放相关单测与界面自检全绿。

### 补充：用户第二次实测仍有游离窗口 → 根因是"Qt 说可见 ≠ X 已映射"

用户第二次反馈：GUI 里在放 4K 视频，**同时**屏幕右侧又有一个 `VLC media player`
窗口在放同一个视频（超出 GUI 窗口范围）。

这次量到了真相（Xvfb 真显示）：

```
① 还没 show 的窗口 → 窗口已映射: False ｜ map_state: 0
② show 之后        → 窗口已映射: True  ｜ map_state: 2
```

也就是说：**Qt 的 `isVisible()/isExposed()` 说"可见"，并不代表 X 服务器已经把窗口
映射到屏幕上**。而 `_已映射()` 原来信的就是 Qt —— 于是 libvlc 在"窗口还没上屏"时
拿到句柄，找不到可用父窗口，就**自己开一个顶层窗口**放画面。

修法（针对根因）：

1. `游离窗口.映射状态()/窗口已映射()`：**直接问 X**（`XGetWindowAttributes.map_state`），
   以 `IsViewable(2)` 为准；
2. `播放页面._已映射()` 改成以 X 的状态为准（Qt 状态只作兜底）—— **窗口没真的上屏就
   不把句柄交给 libvlc**，从源头上不产生游离窗口；
3. `播放页面._自愈画面()`：收回之前先确认"我的窗口真的在屏幕上"，没上屏就 0.5 秒后
   再来（最多 10 次），避免"把画面又绑到无效句柄 → 又一个游离窗口"；
4. `游离窗口.销毁窗口()`：**连子窗口一起销毁**（只销毁父窗口会留下 vout 子窗口，
   用户会看到"窗口没了画面还在"）；新增 `清干净游离窗口()`：反复"找→销毁"直到干净；
5. 守卫到自愈上限后调用 `清干净游离窗口()`，并提示手动恢复方式。

验证（Xvfb 真显示）：映射判断 ①② 正确；真起独立 vlc → 找到 2 个游离窗口 →
`清干净游离窗口(3)` 处理 2 次 → 剩 0 个。自检 502 项全绿（新增 2 条映射断言）、
单测 649 项全绿。

### 第三次反馈后的最终定位：**两个播放窗口的"就绪判断"不统一**

用户第三次实测：主程序窗口里在放（4K HEVC，硬解 vaapi），同时屏幕上另一个
`VLC media player` 窗口也在放。观察到一个**决定性细节**：

> 那个多出来的窗口标题是 **`VLC media player`** —— 不是我们的
> `🎬 文件名`（独立窗口的标题）也不是 `网盘管理 V8_3`。
> 也就是说：**那是 libvlc 自己开的顶层窗口**，不是我们的"独立窗口"。

而它为什么会出现？把两条路都比过之后很清楚：

两个窗口各有各的判断，修了一个漏了另一个 —— 这就是"修了还有"的原因。

**最终修法：把判断收敛成唯一入口** `v8_3/界面/窗口就绪.py`

* `窗口就绪(部件, 重试上限)`：以 **X 的 `map_state == IsViewable(2)`** 为准，
  Qt 的 `isVisible/isExposed` 只作兜底；非 X11 平台/拿不到状态直接放行（别卡住起播）；
* 播放页与独立窗口的 `_已映射()` 都改成调用它（老实现保留为 `_已映射_旧()` 兜底）；
* 两个窗口起播前都**轮询等窗口上屏**（90ms × 最多 28 次 ≈ 2.5 秒），
  超时就明确说"窗口迟迟没上屏，先不起播（避免多出 VLC 窗口）"，而不是硬播；
* `播放核心.关闭()` 里再兜一层：清掉可能残留的游离窗口。
